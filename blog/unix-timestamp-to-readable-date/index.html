How to Convert a Unix Timestamp to a Readable Date

September 21, 2026

You open a server log, an API response, or a database row and instead of a date you get a number like `1758000000`. That's a Unix timestamp — and once you know how to read it, it's actually one of the simplest date formats there is. Here's what that number means, why it sometimes has three extra digits, how timezones fit in, and the one edge case worth knowing about before you trust a timestamp far in the future.

What a Unix timestamp actually is

A Unix timestamp (also called Unix time, epoch time, or POSIX time) is simply the number of seconds that have passed since a fixed starting point: midnight UTC on January 1, 1970 — the "Unix epoch." `1758000000` means "1,758,000,000 seconds after that moment," which works out to September 16, 2025. There's no month, day, or timezone baked into the number itself — it's a single, ever-increasing count that any system, in any timezone, can convert into the same exact instant. That's the whole appeal: computers are much better at comparing and storing one plain integer than parsing a hundred different date-string formats.

Seconds vs. milliseconds — the most common mix-up

The classic Unix timestamp is in seconds, which is what you'll get from most Unix/Linux tools, PHP's `time()`, and many backend APIs. But JavaScript's `Date.now()` and a lot of web-facing APIs return milliseconds instead — the same idea, just 1,000x more precise. The quick way to tell which one you're looking at: a current seconds-based timestamp is 10 digits long (like `1758000000`), while a current milliseconds-based one is 13 digits (like `1758000000000`). Feeding a milliseconds value into a function that expects seconds lands you somewhere in the year 55,700 — and feeding a seconds value into a function expecting milliseconds lands you back in 1970 — both instantly obvious once you know what to check for.

Timezones: the timestamp itself doesn't have one

Because a Unix timestamp counts seconds since a single global instant, it's inherently timezone-free — `1758000000` refers to the exact same moment everywhere on Earth. What changes by timezone is only how that moment gets *displayed*: converted to UTC it might read "16:00," while converted to your local timezone it might read "09:00" or "19:00," depending on where you are. This is actually the main reason developers like storing timestamps this way — the raw number never needs adjusting when a user changes location or daylight saving time shifts; only the final display step needs to know which timezone to render it in.

The Year 2038 problem, briefly

Older systems store a Unix timestamp as a signed 32-bit integer, which can only count up to 2,147,483,647 seconds after the epoch — a limit reached at 03:14:07 UTC on January 19, 2038. After that instant, a 32-bit signed timestamp overflows and wraps around to a negative number, which typically gets misread as a date back in December 1901. Most modern systems, languages, and databases have already moved to 64-bit timestamps (which won't run out for billions of years), so this mostly matters for older embedded systems and legacy 32-bit software — but it's worth knowing about if you're ever debugging a date that mysteriously jumped to 1901.

Quick reference

  • 10-digit number (like `1758000000`)? That's seconds — the classic Unix timestamp format.
  • 13-digit number (like `1758000000000`)? That's milliseconds — common in JavaScript and many web APIs.
  • Need to go the other way — a date into a timestamp — for an API request or a database query? Pick a date and time and read off both the seconds and milliseconds versions at once.
  • Debugging a date that looks wildly wrong (either 1901 or far in the future)? Check for a seconds/milliseconds mix-up first, then a possible 32-bit overflow if the date involved is near or after 2038.
